# mTLS Multi-Cert Client Identity Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let `inbound-gateway` distinguish between individually-issued client certificates (same demo CA) and forward each caller's CN + fingerprint to the first-hop service (service-a, service-c), which surfaces it in the JSON response.

**Architecture:** `scripts/gen-certs.sh` mints two additional named client certs (alice, bob) off the existing demo CA. The `ClientTrafficPolicy` gains `headers.xForwardedClientCert` (mode `SanitizeSet`, `certDetailsToAdd: [Subject]`), so Envoy sets a trustworthy `x-forwarded-client-cert` (XFCC) header — `Hash=<fingerprint>;Subject="CN=<name>"` — on every request it forwards. A new `internal/certident` package parses that header; `internal/servicea` and `internal/servicec` call it and add an optional `client` field to their existing JSON response. `scripts/demo.sh` gets a new step proving alice/bob are distinguished.

**Tech Stack:** Go 1.27, Envoy Gateway v1.2.5 (`gateway.envoyproxy.io/v1alpha1` CRDs — `ClientTrafficPolicy`), Helm, bash + curl + openssl.

**Spec:** `docs/superpowers/specs/2026-09-10-mtls-client-identity-design.md`

## Global Constraints

- Go module name: `envoy-experiment`; Go `1.27.0` (see `go.mod`).
- Envoy Gateway Helm chart pinned to `v1.2.5`; `ClientTrafficPolicy` is apiVersion `gateway.envoyproxy.io/v1alpha1`. Its XFCC-forwarding field is `spec.headers.xForwardedClientCert` (NOT `spec.tls.clientCertificate` — verified against the actual v1.2.5 CRD Go types), with `mode` one of `Sanitize;ForwardOnly;AppendForward;SanitizeSet;AlwaysForwardOnly` and `certDetailsToAdd` one of `Subject;Cert;Chain;DNS;URI` (max 5 items). `Hash` is always included automatically once any detail is forwarded — it must NOT be listed in `certDetailsToAdd`.
- Auth model is unchanged: mTLS remains mandatory at the listener (already enforced by `ClientTrafficPolicy`'s `tls.clientValidation`), JWT remains required on `/a` and `/c`. This feature adds identity context only — it must never become a second grant of access.
- Cert identity propagation is scoped to the first hop only (service-a, service-c). Do not thread it through to service-b/service-d/token-service.
- All demo mTLS PKI lives in the git-ignored `.certs/` directory, generated by `scripts/gen-certs.sh`; never commit key material.
- Working dir for all commands: `/Users/luispessoa/development/envoy-experiment`.
- Commit messages end with trailer: `Co-authored-by: Copilot <223556219+Copilot@users.noreply.github.com>`.

// Package certident parses the client certificate identity that
// inbound-gateway forwards via the standard XFCC ("x-forwarded-client-cert")
// header, produced by the ClientTrafficPolicy's headers.xForwardedClientCert
// setting (mode SanitizeSet, certDetailsToAdd: [Subject]; Hash is always
// included automatically). Envoy renders that header as semicolon-separated
// key=value pairs, e.g.:
//
//	Hash=ab12...;Subject="CN=alice"
//
// This package extracts just the two fields callers need: the certificate's
// Subject Common Name (CN) and its SHA-256 fingerprint (Hash).
package certident

import "strings"

// Identity is the parsed client-certificate identity forwarded by the
// gateway. JSON tags match the "client" field services embed in their
// response bodies.
type Identity struct {
	CN          string `json:"cn"`
	Fingerprint string `json:"fingerprint"`
}

// Parse extracts CN and fingerprint (Hash) from a raw XFCC header value.
// ok is false if the header is empty or no CN could be found in the
// Subject field.
func Parse(xfcc string) (Identity, bool) {
	if xfcc == "" {
		return Identity{}, false
	}

	var hash, subject string
	for _, part := range strings.Split(xfcc, ";") {
		key, value, found := strings.Cut(part, "=")
		if !found {
			continue
		}
		value = strings.Trim(value, `"`)
		switch key {
		case "Hash":
			hash = value
		case "Subject":
			subject = value
		}
	}

	cn := extractCN(subject)
	if cn == "" {
		return Identity{}, false
	}
	return Identity{CN: cn, Fingerprint: hash}, true
}

// extractCN pulls the CN=<value> attribute out of a comma-separated DN
// string such as "CN=alice,O=demo".
func extractCN(subject string) string {
	for _, attr := range strings.Split(subject, ",") {
		key, value, found := strings.Cut(attr, "=")
		if found && key == "CN" {
			return value
		}
	}
	return ""
}
```

# Enforces mutual TLS on the Gateway's listener: clients must present a
# certificate signed by the CA in the referenced Secret or the TLS handshake
# is rejected before any routing or JWT logic runs. Also forwards each
# validated client certificate's Subject (CN) and fingerprint (Hash, added
# automatically by Envoy) to downstream services via the standard
# x-forwarded-client-cert (XFCC) header, so services can distinguish callers
# without doing their own cert parsing.
apiVersion: gateway.envoyproxy.io/v1alpha1
kind: ClientTrafficPolicy
metadata:
  name: {{ .Values.gatewayName }}-mtls
  namespace: {{ .Values.namespace }}
spec:
  targetRefs:
    - group: gateway.networking.k8s.io
      kind: Gateway
      name: {{ .Values.gatewayName }}
  tls:
    clientValidation:
      caCertificateRefs:
        - kind: Secret
          name: {{ .Values.tls.caSecretName }}
  headers:
    xForwardedClientCert:
      mode: SanitizeSet
      certDetailsToAdd:
        - Subject
```

```markdown
**Client-certificate identity rides the XFCC header to the first hop
only.** `inbound-gateway`'s `ClientTrafficPolicy` also sets
`headers.xForwardedClientCert` (mode `SanitizeSet`, forwarding `Subject`;
`Hash` is added automatically), so every request forwarded to service-a or
service-c carries a `x-forwarded-client-cert` header Envoy itself
generated from the certificate it just validated — never something a
client could spoof. `internal/certident` parses it into a CN + fingerprint
pair that both handlers add to their JSON response under `client`. This
stays deliberately shallow: it does not propagate past the first hop
(service-b, service-d, and token-service never see it), and it is not a
second authentication path — JWT still gates `/a` and `/c`; the cert only
answers "who is this," not "what may they do."
```
